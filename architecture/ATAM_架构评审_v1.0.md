## 3. 架构分析方法

### 3.1 每个质量属性场景的架构分析

#### P1 — 调度延迟 < 1s

**架构方法**：
- APScheduler BackgroundScheduler + ThreadPoolExecutor(max_workers=10)
- 任务注册在内存中完成，调度决策在 APScheduler 内部线程池

**分析结论**：✅ **非风险**
- APScheduler 内部使用高效的事件循环，100 个任务的调度分发在毫秒级完成
- ThreadPoolExecutor 支持并发执行，不会因串行调度产生延迟

**敏感点**：max_workers 配置值（过小会导致并发不足）

---

#### P2 — SQLite 写入 < 10ms

**架构方法**：
- SQLite WAL 模式，读写分离
- threading.Lock 保证线程安全
- 单次 INSERT 操作

**分析结论**：✅ **非风险**
- WAL 模式下读不阻塞写，写入性能显著提升
- 单次 INSERT 操作通常在 1-5ms 内完成
- 已在 ADR-002 中验证选型合理性

**敏感点**：并发写入频率（超过 100 次/秒时可能出现竞争）

---

#### P3 — 崩溃恢复 < 5s

**架构方法**：
- SQLite WAL 自动崩溃恢复（journal replay）
- 任务定义从 TaskRegistry 内存加载（非 SQLite 恢复）
- 调度器启动时重新注册所有活跃任务到 APScheduler

**分析结论**：✅ **非风险**
- SQLite WAL 恢复通常在毫秒级
- 任务注册是内存操作 + SQLite upsert，100 个任务在秒级完成
- 心跳机制可在 60 秒内检测到异常

**敏感点**：任务数量（超过 1000 个任务时注册可能变慢）

---

#### R1 — 任务失败重试

**架构方法**：
- RetryPolicy 指数退避 + 随机抖动
- TaskExecutor 处理重试决策
- TaskResult.skip_retry 支持业务层控制

**分析结论**：✅ **非风险**
- 重试策略参数可配置，适应不同场景
- 指数退避避免重试风暴
- 随机抖动降低并发碰撞

**权衡点**：重试间隔 vs 业务实时性
- 首次重试 60s+，对实时性要求高的任务可能不满足
- 缓解：每个任务可独立配置重试参数

---

#### R2 — 死信隔离

**架构方法**：
- RetryPolicy.is_dead_letter() 判定 DLQ 条件
- 达到 max_retries 或 skip_retry=True 进入 DLQ
- Notifier.alert_task_dlq() 发送严重告警
- CLI dlq 命令查看死信队列

**分析结论**：✅ **非风险**
- DLQ 状态持久化到 SQLite，不会丢失
- 告警机制保证运维人员及时感知
- CLI 提供查看和管理手段

**敏感点**：DLQ 任务无自动重试机制（需人工介入）

---

#### R3 — 超时终止

**架构方法**：
- 线程 join(timeout) + daemon 线程
- 超时后主线程继续，daemon 线程自动清理
- 超时结果标记 TASK_TIMEOUT(SCH-04-002)

**分析结论**：⚠️ **风险（低风险）**
- daemon 线程无法被强制终止（Python 线程模型限制）
- 对于阻塞 I/O（如网络请求挂起），daemon 线程会持续占用资源
- 线程池 worker 在 daemon 线程结束前不会释放

**缓解措施**：
1. 文档说明超时行为，建议任务函数内部设置 I/O 超时
2. 对于关键任务，推荐使用 timeout 参数 + 函数内 signal/socket timeout
3. 未来版本可考虑 multiprocessing 方案（ADR-005 已分析）

---

#### S1 — 密钥零入库

**架构方法**：
- 项目铁律 §0 授权铁律约束
- .secrets/ 目录 gitignore
- 代码审查流程

**分析结论**：✅ **非风险**
- 铁律卡全程强制生效
- 代码中未发现硬编码密钥的模式
- .gitignore 已配置排除敏感文件

**敏感点**：Webhook URL 可能包含 Token（已在 notifier.py 中截断错误消息）

---

#### S2 — 操作可追溯

**架构方法**：
- SQLite + CSV 双写（ADR-006）
- ExecutionRecord 16 字段完整记录
- 幂等键记录保证去重可追溯

**分析结论**：✅ **非风险**
- 每次执行产生完整记录（run_id、时间、状态、错误码、结果）
- CSV 追加模式保证历史不可篡改
- SQLite 支持程序化查询和统计

---

#### M1 — 模块替换

**架构方法**：
- 五层管道单向数据流（ADR-008）
- 全局单例 + 依赖注入接口（set_config 等）
- SchedulerManager 抽象层隔离 APScheduler

**分析结论**：✅ **非风险**
- 调度内核替换仅需修改 SchedulerManager + ADR-001
- StateStore 替换仅需修改 state_store.py + ADR-002
- 模块间通过单例接口通信，替换不影响上层

**权衡点**：全局单例 vs 依赖注入
- 单例简化使用但降低测试灵活性
- 当前方案适合单进程场景，未来如需多实例需重构

---

#### M3 — 独立测试

**架构方法**：
- 模块间通过接口依赖，可 mock
- models.py / utils.py 无外部依赖
- StateStore 可通过传入 db_path 创建测试实例

**分析结论**：⚠️ **风险（低风险）**
- 全局单例在测试间需要手动重置
- 部分模块直接调用 get_config() 获取全局配置，测试时需要 set_config() 注入
- 缺少 fixture 和 conftest.py 基础设施

**缓解措施**：
1. 开发阶段创建 tests/conftest.py，提供临时数据库和配置 fixture
2. 每个模块的 get_xxx() 单例函数支持重置（测试前清理）

---

#### U1 — 装饰器注册 3 行代码

**架构方法**：
- @register_task 装饰器（ADR-010）
- 默认值覆盖常见场景（trigger="cron", idempotency_key="{date}"）

**分析结论**：✅ **非风险**
```python
@register_task(name="my_task", trigger="cron", hour=2)
def my_task():
    pass
```
- 确实 3 行代码完成注册
- 默认值合理（max_retries=3, timeout=300）

## 5. 敏感点与权衡点

### 5.1 敏感点（Sensitivity Points）

| 编号 | 敏感点 | 影响的质量属性 | 关联组件 | 说明 |
|-----|--------|-------------|---------|------|
| SP-001 | max_workers 配置 | 性能 | SchedulerManager | 值过小导致并发不足，过大浪费资源 |
| SP-002 | retry_base_delay | 可靠性/性能 | RetryPolicy | 值过小可能加重下游负担，过大影响恢复速度 |
| SP-003 | misfire_grace_time | 可靠性 | SchedulerManager | 值过小导致任务跳过，过大导致堆积 |
| SP-004 | 幂等键表达式选择 | 正确性/性能 | IdempotencyManager | 粒度过粗导致误跳过，过细失去去重意义 |
| SP-005 | heartbeat 间隔 | 可靠性 | SchedulerManager | 间隔过长导致误报，过短增加 I/O |

### 5.2 权衡点（Tradeoff Points）

| 编号 | 权衡点 | 选项 A | 选项 B | 决策 | 理由 |
|-----|--------|--------|--------|------|------|
| TP-001 | 超时控制策略 | 线程 join（当前） | multiprocessing + terminate | 选择 A | 跨平台简单，代价是阻塞 I/O 场景不精确 |
| TP-002 | 全局单例 vs 依赖注入 | 全局单例（当前） | 完整 DI 容器 | 选择 A | 单进程简单性优先，代价是测试需手动重置 |
| TP-003 | 双写 vs 单写 | SQLite + CSV（当前） | 仅 SQLite | 选择 A | 审计需求强制 CSV，代价是少量写入开销 |
| TP-004 | 重试间隔 | 60s 起步（当前） | 秒级起步 | 选择 A | 防止重试风暴，代价是实时恢复较慢 |
| TP-005 | 配置热更新 | 不支持（当前） | 支持热更新 | 选择 A | 实现简单，代价是配置变更需重启 |
